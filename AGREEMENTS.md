# Соглашения по проекту «Chicano Barbershop»

> Живой документ. Дополняется по ходу работы. Последнее обновление: 2026-09-01

## 1. Коммуникация

| Что | Соглашение |
|-----|------------|
| Язык общения с ассистентом | **Русский** |
| Язык кода, комментариев, коммитов | **Английский** |
| Язык интерфейса (UI) приложения | **Английский** (возможен перевод на русский в будущем — тексты держим готовыми к вынесению в словарь) |
| Данные в БД (товары, услуги) | Названия/описания на русском там, где так задал заказчик; остальное — английский |

## 2. Технологический стек

| Слой | Решение | Примечание |
|------|---------|------------|
| Фреймворк | **SvelteKit 2 + Svelte 5** (runes: `$state`, `$derived`, `$props`) | Никакого legacy-синтаксиса (`export let`, `$:`) |
| Стили | **Tailwind CSS v4** | Конфиг через `@theme` в CSS, плагин `@tailwindcss/vite`. Файла `tailwind.config.js` нет |
| БД | **SQLite** через `better-sqlite3` | Синхронный API, файл `data/chicano.db` |
| Язык | **JavaScript + JSDoc** | Без TypeScript-компиляции |
| Сборка / dev | Vite (входит в SvelteKit) | `npm run dev` |
| Адаптер | `@sveltejs/adapter-auto` | Для прототипа достаточно |

## 3. Архитектурные договорённости

1. **Вся работа с БД — только на сервере**: `src/lib/server/db.js`. Клиент никогда не импортирует `better-sqlite3`.
2. **Загрузка данных** — через `+page.server.js` (`load`), мутации — через **form actions** (`export const actions`), прогрессивное улучшение через `use:enhance`.
3. **Авторизация — симуляция**: логин по e-mail без пароля. Сессия = случайный токен в таблице `sessions`, кладётся в httpOnly-cookie `session_id`. Пользователь резолвится в `hooks.server.js` → `event.locals.user`.
4. **Корзина** — серверная, в таблице `cart_items`, привязана к сессии/пользователю. Симуляция заказа: кнопка «Checkout» очищает корзину и показывает уведомление.
5. **Уведомления (toast)** — глобальный стор `src/lib/stores/toast.svelte.js`, компонент в корневом layout.
6. **Схема БД** создаётся и наполняется идемпотентно при старте (`CREATE TABLE IF NOT EXISTS` + сид, если таблица пуста).

## 4. Дизайн-система (стиль Chicano)

| Токен | Значение | Где применяем |
|-------|----------|---------------|
| Фон | `#09090b` / `slate-950` | Основа страницы |
| Поверхность | `zinc-900/40` | Карточки, панели |
| Границы | `border-zinc-800` | Все рамки по умолчанию |
| Акцент (золото) | `#D4AF37` (`--color-gold`) | Кнопки, активные состояния, hover-рамки |
| Текст | `zinc-100` / `zinc-400` (вторичный) | |

- **Шрифты**: готический/блэклеттер (`UnifrakturMaguntia`) — только для крупных заголовков; `Oswald` — подзаголовки/навигация (uppercase, широкий трекинг); `Inter` — основной текст.
- **Эстетика**: мрачная брутальная роскошь лоурайдеров и тату-культуры. Тонкие золотые линии-разделители, декоративные SVG-иконки собственной отрисовки (никаких иконочных библиотек).
- **Mobile-first**: базовые стили — под смартфон, десктоп добавляется через `sm:` / `md:` / `lg:`.
- Анимации сдержанные: `transition-colors`, лёгкий `hover:-translate-y-0.5`. Никакого «карнавала».

## 5. Структура проекта

```
src/
  lib/
    server/db.js        — подключение к SQLite, схема, сид, запросы
    components/         — переиспользуемые Svelte-компоненты
    stores/             — глобальное состояние (toast, cart-count)
  routes/
    +layout.svelte      — шапка, футер, toast-контейнер
    +page.svelte        — главная
    login/              — симуляция авторизации
    booking/            — запись на стрижку
    shop/               — магазин
    cart/               — корзина
    account/            — мои записи
data/chicano.db         — файл БД (в .gitignore)
```

## 6. Прочее

- Демо-товары магазина ведут на внешние ссылки (Ozon) — открываются в новой вкладке (`target="_blank" rel="noopener noreferrer"`).
- Прототип не предназначен для продакшена: нет паролей, платежей и валидации уровня боевой системы. Это заявлено осознанно.
- Файл БД пересоздаётся командой `npm run db:reset`.

## Журнал изменений соглашений

- **2026-09-01** — документ создан; зафиксированы язык общения, стек, дизайн-токены и архитектура прототипа.
- **2026-09-01** — решения, принятые при сборке первого прототипа:
  - Товары магазина хранятся ровно в том виде, в котором их задал заказчик (русские
    названия и описания). Обвязка интерфейса остаётся английской. Кнопки
    «Купить на Ozon» и «В корзину» оставлены по-русски — так они были названы в ТЗ.
  - Каталог дополнен двумя позициями категории «Лицо» (Proraso, Baxter), чтобы закрыть
    требование «средства для ухода за лицом». Первые четыре товара — из ТЗ, без изменений.
  - Корзина работает без авторизации (гостевой cookie `chicano_cart`); аккаунт требуется
    только на шаге оформления заказа — так симуляция авторизации делает реальную работу.
  - Форма записи для незалогиненного гостя одновременно создаёт аккаунт: никто не
    перенабирает бронь после логина.
  - Подтверждения записи и заказа рендерятся из результата form action (`$derived`, не
    `$effect`) — иначе они не работают при отключённом JS.
  - Плагин SvelteKit импортируется из `@sveltejs/kit/vite` (в vite-plugin-svelte 7 его нет).
  - Cookie выставляются с `secure` только на https — иначе браузер отбрасывает их
    при заходе с телефона на `http://<LAN-адрес>:5173`.
- **2026-09-01** — админ-панель `/admin`:
  - Доступ = авторизован + флаг `users.is_admin`. Флаг выдаётся один раз по пасскоду
    на `/admin/unlock` (по умолчанию `chicano`, переопределяется `ADMIN_PASSCODE` в `.env`).
  - Демо-пользователь `demo@chicano.shop` намеренно НЕ админ: авторизация симулированная,
    его почту может ввести кто угодно, и флаг обошёл бы пасскод.
  - Guard вызывается в load каждой админской страницы (`requireAdmin`), а не только в
    layout: load лэйаута не защищает вложенные страницы — их load выполняется независимо.
  - Удаление услуги или мастера блокируется, если на них есть записи. История важнее.
  - Слаги генерируются автоматически с транслитерацией кириллицы и суффиксом `-2`, `-3`
    при коллизии.
  - Схема правится через `ensureColumn()` — существующие БД мигрируют без сброса.

- **2026-09-01** — редактирование услуг и товаров:
  - Режим правки — через query-параметр `?edit=<id>` на той же странице, а не отдельный
    маршрут. Ссылка работает без JS, шарится, а форма создания переиспользуется целиком.
    После сохранения — `redirect(303)` на чистый список.
  - Валидация вынесена в общий `readService()` / `readProduct()`: create и update
    расходятся только в том, что делают с результатом.
  - При ошибке отправки `form.values` перекрывает загруженную строку, чтобы набранное
    не потерялось.
  - `uniqueSlug()` принимает `exceptId` — строка сохраняет свой слаг при правке, а чужой
    занятый получает суффикс.
  - **Цена записи замораживается** в `appointments.price` в момент бронирования.
    Иначе правка цены услуги задним числом переписывала бы историю: и `/account`, и
    админка читали цену джойном к `services`. Запросы используют
    `COALESCE(a.price, s.price)` — старые строки без снимка падают на текущую цену.
  - У товаров такой проблемы нет: заказы хранят замороженную JSON-копию позиций.
    Живые корзины, наоборот, показывают актуальную цену — до оформления это верно.

- **2026-09-01** — редактирование мастеров по той же схеме `?edit=<id>`. Записи остаются
  привязанными к мастеру: `appointments.barber_id` не меняется, а в дневнике и в кабинете
  клиента отображается уже новое имя — для смены псевдонима это верно.

- **2026-09-01** — редактирование записей на стрижку:
  - Можно менять услугу, мастера, день, время, заметку и клиента. Другой e-mail переносит
    запись на этого клиента (тот же `findOrCreateUser`, что и при создании).
  - Проверка занятости слота исключает саму редактируемую запись (`freeSlotsOn(..., exceptId)`),
    иначе сохранение без переноса конфликтовало бы само с собой. То же в `availabilityGrid`
    и в действии `restore`.
  - **Цена**: перенос дня/времени/мастера сохраняет замороженную цену; смена самой услуги
    переоценивает по её текущей цене. Молча переоценивать перенос — обман клиента.
  - Форма вынесена в `BookingForm.svelte` и оборачивается в `{#key editing?.id}`. Без этого
    при переходе между `?edit=N` компонент не перемонтируется (тот же маршрут), и состояние
    выбора мастера/даты осталось бы от предыдущей записи.

- **2026-09-01** — раздел `/admin/clients`: список, поиск, добавление, правка, удаление.
  - E-mail — это идентичность (вход матчится по нему), поэтому коллизия при правке
    отклоняется с указанием, кому адрес принадлежит, а не сливает записи молча.
    Смена адреса меняет и способ входа — предупреждение стоит прямо под полем.
  - Удаление запрещено, если у клиента есть записи или заказы: `appointments` каскадно
    удалились бы вместе с ним. Также нельзя удалить аккаунт, под которым вошёл сам админ.
  - Поиск — обычная GET-форма, запрос живёт в URL и переживает перезагрузку.
  - Флаг `is_admin` показан бейджем, но не редактируется: выдача прав — отдельная
    операция, её место в пасскод-потоке, а не в форме правки контактов.

- **2026-09-01** — переключатель прав администратора в списке клиентов (Grant / Revoke).
  - Свои права поменять нельзя: отзыв у себя выкинул бы на пасскод-гейт на следующем клике.
    В своей строке вместо кнопки — неактивный статус и пометка «you».
  - На странице стоит явное предупреждение: вход симулированный, поэтому права, выданные
    на адрес, получит любой, кто этот адрес введёт. Обращаться с «Grant» как с паролем.
  - Пасскод `/admin/unlock` остаётся запасным входом, так что «последнего админа» как
    точки невозврата здесь нет — отдельная защита не нужна.

- **2026-09-01** — SMS: напоминания за 24 ч и за 1 ч, плюс форс-мажорная рассылка.
  - Отправка через сменный драйвер (`src/lib/server/sms.js`). По умолчанию симулированный:
    очередь и журнал ведутся по-настоящему, наружу ничего не уходит. Боевой драйвер SMS.ru
    включается `SMS_PROVIDER=smsru` + `SMS_API_KEY`. Аккаунт шлюза — на стороне заказчика.
  - Всё идёт через одну таблицу `notifications`, воркер разгребает её раз в минуту. Отсюда
    два свойства: дважды не отправится (частичный UNIQUE-индекс по `appointment_id, kind`)
    и не потеряется, если сервер лежал.
  - `send_at` хранится как epoch-миллисекунды, а не как текст. Записи живут в локальном
    времени (`date` + `time`), а `datetime('now')` в SQLite — UTC; сравнивать их означало бы
    ловить сдвиг на часовой пояс. Эпоха снимает вопрос целиком.
  - Напоминание, просроченное больше чем на 6 ч, помечается `expired` и НЕ отправляется.
    После ночного простоя клиент не должен получить вчерашнее «через час».
  - `syncReminders(id)` вызывается после любого изменения записи — создание, перенос,
    отмена, восстановление. Одна функция вместо логики в четырёх местах.
  - Клиент без телефона — статус `skipped` с причиной, а не тихий пропуск: экран рассылки
    показывает поимённо, кому придётся звонить.
  - Отправка рассылки требует вписать число получателей руками. Разослать всему дню
    одним кликом — слишком легко ошибиться.
  - Тексты автоматических напоминаний правятся в коде: заказчик решил, что редактор
    в интерфейсе не нужен.
  - Тест `npm run test:sms` — чёрный ящик: все мутации через HTTP, проверки чтением БД.
    Импортировать модули приложения напрямую нельзя — `$env/dynamic/private` резолвится
    только внутри Vite.

- **2026-09-01** — охват рассылки «все зарегистрированные» (для поздравлений и объявлений).
  - Считается по клиентам, а не по записям: у кого три брони — получит одно сообщение.
  - Плейсхолдеры записи (`{date}`, `{time}`, `{service}`, `{barber}`) при этом охвате
    подставить не из чего. Отправка с ними отклоняется — иначе клиенту ушли бы фигурные
    скобки буквально. Работает только `{name}`, о чём написано прямо под полем.
  - Шаблон по умолчанию для этого охвата — новогоднее поздравление, а не текст про аварию.

- **2026-09-01** — фикс горизонтальной прокрутки на `/booking` (телефон).
  У `<fieldset>` по умолчанию `min-inline-size: min-content`, поэтому он отказывается быть
  уже своего самого широкого содержимого. Внутри одного такого лежит лента дней с
  `overflow-x: auto` — fieldset растягивался до 1000px и утаскивал всю страницу вбок,
  сводя на нет собственную прокрутку ленты. Лечится одной строкой `fieldset { min-inline-size: 0 }`
  в базовом слое. Правило общее, не точечное: любой будущий fieldset с широким содержимым
  наступил бы на те же грабли.
  Замер: скрипт сравнивает `documentElement.scrollWidth` с `clientWidth` на 320/360/390/414px
  по всем публичным страницам. До фикса `/booking` вылезала на 642–712px, остальные чистые.

- **2026-09-01** — читаемость: контраст отключённых состояний и типографика.
  - Занятый слот времени имел контраст текста **1.91:1** (`text-zinc-700` на почти чёрном)
    и рамку 1.12 — ячейка исчезала целиком, из-за чего сетка выглядела рваной. Стало
    `text-zinc-500` + `border-zinc-800` → **4.22:1**, ячейка видна, зачёркивание оставлено.
  - Полностью занятый день в ленте больше не гасится через `opacity-30`: дата и слово
    «full» должны читаться, иначе чип выглядит дырой, а не занятым днём. Слово «full»
    подсвечено акцентом `text-flash`.
  - Шрифты: 23 произвольных размера `text-[Nrem]` (нижний — 0.45rem, то есть **7.2px**)
    схлопнуты в 8 ступеней с полом 0.7rem (11.2px), 214 замен в 21 файле.
  - Oswald узкий: у `.display` поднят вес до 500, трекинг снижен с 0.18em до 0.12em —
    именно широкий трекинг на мелком кегле превращал подписи в серую кашу. У `.btn`
    вес 600, у `.label` размер 0.8rem и цвет `zinc-400` вместо `zinc-500`.
  - Контраст меряется скриптом: цвета Tailwind v4 приходят в `oklch`, парсить их как RGB
    нельзя — конвертация через canvas, фон собирается композитом по всем родителям с учётом
    альфы. Переполнение проверено на 320/360/390/414 — после укрупнения шрифтов чисто.

### Заметки по окружению (не соглашения, а грабли)

- Windows-шелл ломает кириллицу в аргументах командной строки: строки приходят как
  литеральные `?` (codepoint 63). Тестировать формы с русским текстом только скриптом
  на Node (`fetch`) или через браузер, но не через `curl --data-urlencode` из bash.
- Инструмент Bash здесь спотыкается на длинных heredoc с большим числом кавычек —
  крупные файлы писать целиком, а не дописывать через `cat >>`.
